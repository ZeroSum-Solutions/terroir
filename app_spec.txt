<project_specification>
  <project_name>terroir</project_name>

  <overview>
    Terroir is a wine-management SaaS for restaurants and serious cellars. Staff photograph paper invoices, the system runs Azure OCR + Claude structured extraction to build a typed inventory, and the app surfaces a public wine list, drink-window guidance, pour tracking, and reconciliation against open bottles. Built on Next.js 16 + Supabase + Anthropic Claude, deployed as a single service on Railway.
  </overview>

  <feature_budget>
    Implement all 269 features enumerated in the core_features section below. The product owner approved this count on 2026-07-23, superseding the previous maximum of 200. Treat each "User can…", "System displays…", or "API returns…" assertion as one feature — do NOT split a single assertion into multiple sub-features, and do NOT add features beyond what is enumerated. This approved count OVERRIDES any complexity-tier table you would otherwise apply.
  </feature_budget>

  <core_features>

    <authentication_and_session>
      - User can sign up with email and password via Supabase Auth
      - User can log in at /login and receive a Supabase session cookie
      - User can log out and have the session cookie cleared
      - User can request a password reset email via Supabase Auth
      - User can complete a password reset from the emailed link
      - System redirects unauthenticated requests to (app)/* back to /login
      - System restores session on page refresh via @supabase/ssr cookie helpers
      - System exposes a server-side Supabase client for route handlers
      - System exposes a browser-side Supabase client for client components
      - API returns 401 when an authenticated route is hit without a session
      - API returns 403 when the user is authenticated but not a member of the requested restaurant
      - System enforces Row-Level Security on every table via is_member / is_member_with_role
      - Dev login route bypasses email auth in non-production environments only
    </authentication_and_session>

    <restaurants_and_teams>
      - Owner can create a new restaurant on first login
      - Owner can rename their restaurant
      - Owner can invite a team member by email
      - System creates a row in invitations with a single-use token
      - Invitee can accept an invitation at /invite/[token]
      - System creates a memberships row when an invitation is accepted
      - Owner can assign a role (owner, manager, staff) to each member
      - Owner can revoke a member's access by deleting their membership
      - Owner can resend a pending invitation
      - Owner can cancel a pending invitation
      - Manager can perform inventory and list operations but not delete the restaurant
      - Staff can record pours and view inventory but cannot edit wine lists
      - System enforces role gates via is_member_with_role DB function
      - User can switch between restaurants they belong to via the settings dropdown
      - User can view the team roster on /team with current roles and pending invites
      - API returns 403 when a non-owner attempts an owner-only mutation
    </restaurants_and_teams>

    <invoice_scanning>
      - User can open the camera-based scan UI at /scan on mobile
      - User can upload a single invoice image from the file picker
      - User can upload a multi-page invoice as multiple images in one batch
      - System uploads each image to Supabase Storage under the restaurant's bucket
      - POST /api/scan submits a stored image for OCR processing
      - System calls Azure Document Intelligence and receives raw text plus tables
      - System sends OCR text to Claude with a structured-extraction system prompt
      - Claude returns a typed JSON list of line items (producer, wine, vintage, qty, unit price, currency, format)
      - System validates Claude's response with a Zod schema before any DB write
      - System rejects responses that fail validation and surfaces a user-readable error
      - System deduplicates accidental double-submits via the scan_idempotency table
      - System creates an invoice_scans row capturing OCR + extraction metadata
      - System upserts wines via find_or_create_wines_batch DB function
      - System creates inventory_items for each parsed line item linked to the scan
      - System enriches new wines against the LWIN catalog via match_lwin_batch
      - User can review extracted line items in a side-by-side view against the photo
      - User can edit a parsed line item before committing it to inventory
      - User can delete a parsed line item before committing
      - User can re-run extraction on a stored scan if Claude misread it
      - User can view the full history of past scans at /scans
      - User can drill into a single scan to see its image, OCR text, and resulting inventory
      - User can attach a delivery date and supplier name to a scan
      - System shows extraction confidence per line item when available
      - API returns 422 when no wines could be extracted from the image
      - API returns 429 when the user exceeds the per-minute scan rate limit
      - API rejects images larger than 10 MB
      - API rejects file types other than jpeg, png, heic, and pdf
    </invoice_scanning>

    <bottle_scanning>
      - User can scan an existing bottle's QR code via the /scan-bottle camera UI
      - System decodes the QR payload and looks up the wine by ID
      - User can confirm or correct the wine match
      - User can record the bottle's current section and bin location
      - System creates an inventory_items row when a new bottle is scanned in
      - System rejects QR codes that do not belong to the current restaurant
      - User can scan multiple bottles in rapid succession in a single session
    </bottle_scanning>

    <cellar_and_inventory>
      - User can view the full cellar inventory at /cellar grouped by section
      - User can search wines by producer, varietal, region, or vintage
      - User can filter wines by color (red, white, rose, sparkling, dessert, fortified)
      - User can filter wines by region or country
      - User can filter wines by vintage range
      - User can sort wines by price, vintage, name, or quantity
      - User can drill into a single wine to see its full detail page
      - System displays current quantity, average cost, and last-purchase date per wine
      - System displays inventory by format (750ml, magnum, half, etc.)
      - User can manually adjust a wine's quantity with a reason note
      - System logs every quantity adjustment as an availability_event
      - User can mark a wine as 86'd (unavailable) without deleting it
      - System auto-86s a wine when inventory hits zero via auto_eightysix_on_low_inventory
      - User can un-86 a wine when restocked
      - User can edit a wine's metadata (producer, name, region, varietal, vintage)
      - User can attach tasting notes to a wine
      - User can attach a hero image to a wine in Supabase Storage
      - User can delete a wine if it has no historical pour or scan references
      - User can export the current cellar to CSV via /api/export
      - User can configure cellar sections (e.g., Reds by Region, Cult Cabs, By the Glass) at /cellar/config
      - User can reorder cellar sections via drag-and-drop (dnd-kit)
      - System persists section order in cellar_config
      - User can move a wine between sections with drag-and-drop
      - User can bulk-assign wines to a section
      - System displays low-stock badges when quantity drops below a configurable threshold
      - System displays peak-window badges on wines entering or in their drink window
      - System surfaces wines past their peak window in a "drink now" filter
    </cellar_and_inventory>

    <wine_intelligence>
      - System computes a drink window (start year, peak year, end year) for each wine
      - System computes recommended serving temperature range per wine
      - System computes recommended decant time per wine
      - User can view drink-window guidance on each wine's detail page
      - User can override system-computed drink-window with manual values
      - System flags wines whose vintage falls outside their drink window with a visual cue
      - System enriches imported wines via enrich_wines_batch DB function
      - System batches Claude calls for enrichment to control cost
      - User can request a re-enrichment of a single wine
      - System falls back to LWIN catalog data when Claude has no opinion
      - System never overwrites a manually-set field during enrichment
    </wine_intelligence>

    <wine_lists_editor>
      - User can create a new wine list at /lists with a name and description
      - User can publish or unpublish a wine list
      - User can set a wine list's slug for the public URL
      - System rejects slug collisions across the same restaurant
      - User can clone an existing wine list as a starting point
      - User can archive a wine list without deleting it
      - User can delete an archived wine list
      - User can add a section to a wine list (e.g., Reds, Whites, Champagne)
      - User can rename a section
      - User can reorder sections via drag-and-drop
      - User can delete a section (cascades to its items with confirmation)
      - User can add a wine to a section by searching the cellar
      - User can add a wine to multiple sections at once
      - User can reorder items within a section via drag-and-drop
      - System persists item order via reorder_wine_list_items DB function
      - User can override the public price per list item
      - User can override the display name per list item
      - User can attach a custom blurb per list item
      - User can hide a list item without removing it
      - User can preview a wine list as a guest would see it
      - System auto-removes 86'd wines from published lists (or marks them gray, configurable)
      - User can publish a list to a public slug at /list/[slug]
      - System renders the public list with restaurant branding
      - System exposes wine_published_list_slugs for cross-list lookups
      - User can export a wine list as a print-ready PDF via /api/pdf
      - System generates the PDF via Puppeteer headless Chrome
      - User can download a wine list as CSV
      - User can share the public list URL via the share sheet on mobile
      - User can copy the public list URL with one click
    </wine_lists_editor>

    <public_wine_list>
      - Guest can view a published wine list at /list/[slug] without logging in
      - System renders the list mobile-first with large touch targets
      - System displays the restaurant's name and optional logo at top
      - System groups wines by section in the configured order
      - System shows price, vintage, and producer for each wine
      - System hides 86'd wines or marks them visibly unavailable per restaurant config
      - System renders a printable view at /list/[slug]/print
      - System sets cache-control headers appropriate for a public page
      - System returns 404 for unpublished or nonexistent slugs
      - Guest can switch between multiple published lists if the restaurant has them
    </public_wine_list>

    <pour_and_open_bottles>
      - Staff can record a pour from /cellar against a specific bottle
      - System opens a new bottle if none is currently open for the wine + format
      - System decrements the open bottle's remaining ounces by the pour amount
      - System closes a bottle automatically when remaining drops below a threshold
      - System creates a pour_events row for every pour
      - System maintains the open_bottles table via pour_events_maintain_open_bottle trigger
      - User can cancel/undo the most recent pour
      - User can view all currently open bottles at /cellar/open
      - User can manually open a bottle without recording a pour (e.g., for tasting)
      - User can manually close an open bottle and discard remaining
      - System exposes record_pour DB function as the only write path for pours
      - System rejects pours when no inventory remains
      - User can configure default pour sizes per format (e.g., 5oz red glass)
      - User can record a pour in a custom amount
      - User can attach a note to a pour event
    </pour_and_open_bottles>

    <reconciliation>
      - Manager can run end-of-shift reconciliation at /cellar/reconcile
      - System lists every open bottle with its tracked remaining volume
      - User can enter the actual remaining volume for each open bottle
      - System computes variance and persists adjustments via reconcile_open_bottle
      - User can reconcile all open bottles in one batch via reconcile_open_bottles_batch
      - System logs each reconciliation as an availability_event with the manager's user ID
      - System highlights variances exceeding a configurable threshold
      - User can view reconciliation history with variance trends
      - System enforces manager-or-owner role for reconciliation writes
    </reconciliation>

    <price_comparison>
      - User can view market price comparisons for a wine at /price-comparison
      - System displays the wine's last-paid price next to indicative market data
      - User can flag a wine as overpaid for follow-up
      - User can sort the price-comparison view by variance percentage
      - System highlights wines whose market price has shifted by more than a configurable percent
    </price_comparison>

    <insights_and_analytics>
      - User can view restaurant-level analytics at /insights
      - System shows total inventory value at current cost
      - System shows pour volume by section over a selectable date range
      - System shows top-N wines by pour count
      - System shows top-N wines by revenue (price * pours)
      - System shows wines aging past their drink window
      - System shows scan throughput (invoices processed per week)
      - System shows extraction accuracy (auto-accepted vs. corrected line items)
      - User can change the date range with a quick selector (7d, 30d, 90d, YTD, custom)
      - User can export an insights view as CSV
    </insights_and_analytics>

  <key_interactions>
    <invoice_scan_flow>
      1. User taps Scan FAB on mobile, captures invoice photo
      2. App uploads image to Supabase Storage
      3. App POSTs scan reference to /api/scan
      4. Server runs Azure OCR, then sends text to Claude with extraction prompt
      5. Server validates Claude response with Zod
      6. Server upserts wines via find_or_create_wines_batch
      7. Server creates invoice_scans + inventory_items rows
      8. Server enriches new wines via match_lwin_batch and enrich_wines_batch
      9. Client navigates to scan-review screen with editable line items
      10. User confirms or edits, then commits to inventory
    </invoice_scan_flow>
    <pour_flow>
      1. Staff opens cellar, taps a wine, selects pour
      2. Client POSTs to /api/pour with oz amount
      3. record_pour DB function opens a new bottle if none open
      4. record_pour decrements remaining_oz on the open bottle
      5. UI updates inventory and open-bottle indicators optimistically
    </pour_flow>
    <publish_list_flow>
      1. User edits sections and items in /lists/[id]
      2. User toggles Published, system validates slug uniqueness
      3. Public route /list/[slug] renders for guests with cache headers
      4. Auto-86 logic hides or marks unavailable wines based on cellar_config
    </publish_list_flow>
    <reconcile_flow>
      1. Manager opens /cellar/reconcile at end of shift
      2. UI lists every open bottle with tracked remaining oz
      3. Manager enters actual remaining for each
      4. Client POSTs to /api/reconcile (single or batch)
      5. reconcile_open_bottles_batch persists deltas as availability_events
    </reconcile_flow>
  </key_interactions>
