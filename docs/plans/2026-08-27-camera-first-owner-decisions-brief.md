**Status: nothing below is a decision.** Per the PRD's own decision boundary,
implementers may not infer answers to D-001–D-011, and this brief does not
either — it restates each gate in plain language and proposes one default,
so the owner can approve, reject, or amend each line without reading the
full 577-line PRD/spec pair first. No production code, migration, or
`app_spec.txt` change may start until the owner records approvals here (or
elsewhere) against the source contract.

## How to use this

For each row: approve the recommended default as-is, or write a different
answer. Anything left blank stays open and continues blocking the column it
gates — the implementation spec treats an unresolved decision as "read-only
spike only" (spikes may proceed; production changes may not), not a default.

| ID | Decision, in plain words | Blocks (if left open) | Recommended default | Why this default |
|---|---|---|---|---|
| D-001 | Where does a personal collector's data live: inside the existing restaurant tenant, a new tenant *type* alongside it, or a fully generalized "collection" concept that replaces today's restaurant-shaped tables? | All production work — this is the foundational schema decision everything else sits on. | **New tenant type**, not a reuse of restaurant tenancy and not a full generalization. | Reusing restaurant tenancy risks bleeding personal-collector UI/behavior into restaurant workflows (the audit flagged this — F-14); full generalization is the largest, least reversible migration. A new type is the narrower, reversible middle path. |
| D-002 | Should the camera ever try to identify more than one bottle/label in a single photo (a shelf, a rack, a case), beyond today's one-label-per-photo scan? | Any guided-area or multi-object vision work. | **No — stay single-label only** until a real-photo spike with measured false-positive/false-negative rates exists. | The PRD itself proposes single-label as "the safest first production slice because the existing system already supports it"; there is no feasibility evidence yet to justify more. |
| D-003 | Can a photo, by itself, ever establish *how many* bottles exist (vs. the user typing the quantity)? | Case/rack vision and any reconciliation feature. | **No — quantity stays user-confirmed only**, photos never establish counts. | Broad photo-based counting was already rejected earlier in this package; reopening it without new evidence risks silent, unverifiable inventory counts. |
| D-004 | What are the named states a piece of evidence can be in (e.g. "the vision model guessed this" vs. "the user typed this" vs. "someone physically checked the shelf"), and — as a full state table — which evidence sources establish which states, which actors may cause which transitions, what a correction does, and what happens on downgrade or on a conflict at any strength? | The evidence schema and every acceptance test that depends on it. | **This complete state table. States, weakest to strongest: expected, visually identified, user-confirmed, physically verified. Origins — a fact ENTERS at the state its evidence source class warrants, never higher: purchase/invoice evidence creates `expected` facts only (per PCI-FR-009 it may propose contents but never mark them visually or physically verified), and provider-sync records — if D-008 is ever approved — likewise create `expected` only; a vision result (photo/model, with model/version and confidence recorded) establishes `visually identified`; a user assertion establishes `user-confirmed`; the collector's physical check establishes `physically verified`. Promotions: the system may perform only expected → visually identified (by attaching a vision result) — it may never set a stronger state; every promotion to user-confirmed or physically verified requires the collector's explicit action on that specific fact; no deterministic promotion rules are approved in v1 (the spec permits them; this default approves none). Corrections: a user correction replaces the fact's value and sets its state to user-confirmed — a correction is itself a user assertion — with the superseded value and its evidence retained, never deleted. Conflicts, at every strength: a new observation whose source state is EQUAL to or STRONGER than the stored fact's replaces it at the new observation's state (stronger always supersedes; within the same strength, latest wins), retaining the superseded value and evidence; a new WEAKER-source observation never overwrites a stronger-state fact — it is stored as a conflicting observation and surfaced for the collector to resolve. "Latest" is ordered by the evidence record's capture/observation time — the moment the evidence was observed, which for provider-sync records means the provider's source timestamp — never by sync or ingestion time; equal observation times are broken by later ingestion time; and a submission that is an exact retry or duplicate delivery (same source reference, same value) is idempotent — it deduplicates against the existing evidence record and changes neither value nor state. Downgrades: states never silently downgrade; the one explicit downgrade is that editing a physically-verified fact drops it to user-confirmed, shown to the user at edit time.** | PCI-FR-007 requires the four states stay *distinguishable* and forbids silent strengthening, but the spec's decision table demands more than state names: "a state table with sources, actors, corrections, and downgrade/conflict rules." This default maps every evidence source the spec names (purchase/invoice, provider sync, photo/model, user assertion, physical verification) to the state it can establish and resolves conflicts at every relative strength, so the row is decidable in one approval; every clause is a proposal you can amend — actor-only promotion is the strictest reading and the easiest to relax later (e.g. by approving a deterministic rule), not something already settled. |
| D-005 | Two parts: (a) approve the spec's PROPOSED first-slice constraint — locations limited to existing bins plus the unplaced queue (the spec proposes this but explicitly requires owner approval before WS-00 may treat it as a source requirement); and (b) what location/container model comes AFTER that first slice, and what is hierarchy's first visual representation? | Later schema and any cellar UI beyond a flat bin picker; leaving (a) unapproved also blocks WS-00 itself. | **(a) Approve the proposed first slice as written: existing bins + the unplaced queue, no fake bin for unplaced stock. (b) For the later model: a single level of nesting — a location (room, offsite facility) contains containers (rack, fridge, bin, sealed case), and a bottle lives in exactly one container or the unplaced queue; no deeper recursion (no racks inside racks). First visual representation: a grouped list (location → containers → bottles) — no 3D or graphical grid rendering.** | The first-slice constraint is the spec's own *proposal*, but WS-00's gate says owner approval must be recorded before it becomes a requirement — so approving it is part of this row, not a given. For the later model, one level of nesting covers every domain example the spec names (room, rack, refrigerator, bin, case, partial case) without recursive-tree complexity, and a grouped list is the cheapest truthful rendering that a later visual upgrade can replace without a schema change. The PRD already excludes a 3D cellar renderer. |
| D-006a | Is a typo-tolerant search baseline over existing fields an acceptable first search deliverable — where "typo-tolerant" means the full PCI-FR-011 contract: representative misspellings, apostrophe/diacritic variants (Château vs Chateau, d'Yquem), producer-vs-cuvée ambiguity, plus structured filters over vintage, purchase period, wine color/type, and location? | WS-05's baseline search work. | **Yes — approve the typo-tolerant + structured-filter baseline at the full PCI-FR-011 scope** (misspellings, apostrophe/diacritic variants, producer/cuvée ambiguity, and vintage / purchase-period / color-type / location filters) as the first search deliverable, measured against the approved eval corpus. | It reuses existing tenant data with no new external provider, and it gives a real number to beat before anything fancier is considered. The scope words matter: approving a narrower "typos only" baseline would quietly shrink the PCI-FR-011 contract, so this row names every clause the requirement carries. One dependency the spec makes explicit: the existing caller-controlled security-definer RPCs must gain internal tenant checks BEFORE search broadens (the spec's WS-05 prerequisite) — approving this row includes approving that hardening as part of the baseline work. |
| D-006b | Should search go further into semantic / conversational natural-language retrieval (needs an embedding provider, an index, and a data-retention policy)? | Embeddings work and any conversational search UI. | **Not yet — defer until D-006a's baseline is measured.** | Committing to a provider, index, and retention policy before there's a baseline to compare against risks paying for capability the typo-tolerant search already covers. |
| D-007 | Who can a collector share their cellar with, at what access level, for how long, and how is access revoked and audited? | The sharing/delegated-access feature entirely. | **Defer — ship nothing here for the first release.** If reopened later, default to a single "view-only, time-boxed" role rather than open-ended edit access. | The PRD already marks sharing as an optional slice that doesn't block core completion (audit finding F-05); the abuse cases and RLS surface are real enough to deserve their own dedicated approval later rather than a rushed default now. |
| D-008 | Which external storage/custody provider (if any) gets a real API/export integration, and on what lawful basis (no credential scraping, no bypassing provider controls)? | The provider-adapter feature entirely. | **Defer — no provider named yet; treat as a later, optional phase.** | Same as D-007: the PRD already treats this as non-blocking for core completion, and no provider's API/auth/export terms have been reviewed yet. |
| D-009 | When a bottle's drink window is closing, how does the user find out — an in-app list, or a push/email notification? | The drink-recommendation UI and any notification work. | **In-app shortlist only, ranked by soonest drink-window end; no push or email.** | The PRD's scope explicitly excludes notifications until a channel/infrastructure decision is made, so in-app is the only option actually available to default to. |
| D-010 | How are bottle-label and invoice photos stored and protected — bucket privacy, how long a signed URL stays valid, how long the photo is kept, and what gets scrubbed from logs/Sentry? | Any feature that persists a captured photo as evidence. | **Private per-tenant storage path; signed URLs live 3,600 s (matching what invoice URLs actually use today — approving this row makes that a deliberate policy for label evidence too, not an accident). Deletion follows the photo's OWNING record: a label-evidence photo is deleted when the inventory row it evidences is deleted; an invoice photo is deleted when its `invoice_scans` row is deleted — never when individual inventory rows derived from that invoice are (one invoice feeds many rows). Evidence photos are included in a collector's data export alongside their inventory. Redaction: raw images, invoice contents, purchase details, natural-language queries, and provider credentials never reach general logs or Sentry replay.** | The PRD states the privacy/observability *goals* as non-functional requirements, but the concrete policy — retention, deletion (per owning record), signed-URL TTL, export, and the full redaction list — is exactly what D-010 leaves OPEN (the package's own audit flagged that these lacked a decision gate). This row proposes one complete policy so a single approval closes the decision; amend any clause before approving if you want different terms. |
| D-011 | When the vision model returns several candidate matches for a photographed label, how confident does the top match need to be before the user can accept it with one tap instead of confirming manually? | One-tap confirmation and any claim of "calibrated confidence" in the UI. | **Keep manual confirm-or-correct as the only path until a representative fixture set produces a measured, calibrated threshold.** The current `0.75` cutoff in the code is a heuristic, not a validated threshold, and should not be presented to the user as one. | The audit already flagged the `0.75` value as untested (finding F-09); shipping one-tap acceptance on an unvalidated number would let a wrong match get "confirmed" too easily. |
