# Camera-First Personal Cellar — Owner Decisions Brief

**Status: nothing below is a decision.** Per the PRD's own decision boundary,
implementers may not infer answers to D-001–D-011, and this brief does not
either — it restates each gate in plain language and proposes one default,
so the owner can approve, reject, or amend each line without reading the
full 577-line PRD/spec pair first. No production code, migration, or
`app_spec.txt` change may start until the owner records approvals here (or
elsewhere) against the source contract.

## How to use this

For each row: approve the recommended default as-is, or write a different
answer. Anything left blank stays open and continues blocking the column it
gates — the implementation spec treats an unresolved decision as "read-only
spike only" (spikes may proceed; production changes may not), not a default.

| ID | Decision, in plain words | Blocks (if left open) | Recommended default | Why this default |
|---|---|---|---|---|
| D-001 | Where does a personal collector's data live: inside the existing restaurant tenant, a new tenant *type* alongside it, or a fully generalized "collection" concept that replaces today's restaurant-shaped tables? | All production work — this is the foundational schema decision everything else sits on. | **New tenant type**, not a reuse of restaurant tenancy and not a full generalization. | Reusing restaurant tenancy risks bleeding personal-collector UI/behavior into restaurant workflows (the audit flagged this — F-14); full generalization is the largest, least reversible migration. A new type is the narrower, reversible middle path. |
| D-002 | Should the camera ever try to identify more than one bottle/label in a single photo (a shelf, a rack, a case), beyond today's one-label-per-photo scan? | Any guided-area or multi-object vision work. | **No — stay single-label only** until a real-photo spike with measured false-positive/false-negative rates exists. | The PRD itself proposes single-label as "the safest first production slice because the existing system already supports it"; there is no feasibility evidence yet to justify more. |
| D-003 | Can a photo, by itself, ever establish *how many* bottles exist (vs. the user typing the quantity)? | Case/rack vision and any reconciliation feature. | **No — quantity stays user-confirmed only**, photos never establish counts. | Broad photo-based counting was already rejected earlier in this package; reopening it without new evidence risks silent, unverifiable inventory counts. |
| D-004 | What are the named states a piece of evidence can be in (e.g. "the vision model guessed this" vs. "the user typed this" vs. "someone physically checked the shelf"), and who is allowed to move evidence from a weaker state to a stronger one? | The evidence schema and every acceptance test that depends on it. | **Four states — expected, visually identified, user-confirmed, physically verified — and only an explicit user/actor action may promote one to the next**; nothing is auto-upgraded. | PCI-FR-007 requires the four states stay *distinguishable* and forbids silent strengthening — it does NOT decide who may promote. The spec explicitly leaves room for "an authorized actor or an approved deterministic rule" (its evidence-rules section); recommending actor-only promotion is the strictest reading and the easiest to relax later, but it IS a choice this row is asking you to make, not something already settled. |
| D-005 | Beyond today's existing bins and the "unplaced" queue, should the first slice let a user create new locations/containers (room, rack, fridge, case) or represent hierarchy between them? | Later schema and any cellar UI beyond a flat bin picker. | **No — first slice only offers existing bins or the unplaced queue**; no new location/container creation or hierarchy yet. | This is the PRD's own stated first-slice constraint; it keeps the vertical slice small and defers hierarchy design until there's real usage to design against. |
| D-006a | Is a typo-tolerant / misspelling-tolerant search over existing fields (producer, vintage, color, purchase period, location) an acceptable first search baseline? | WS-05's baseline search work. | **Yes — approve the typo-tolerant + structured-filter baseline** as the first search deliverable, measured against the approved eval corpus. | It reuses existing tenant data with no new external provider, and it gives a real number to beat before anything fancier is considered. One dependency the spec makes explicit: the existing caller-controlled security-definer RPCs must gain internal tenant checks BEFORE search broadens (the spec's WS-05 prerequisite) — approving this row includes approving that hardening as part of the baseline work. |
| D-006b | Should search go further into semantic / conversational natural-language retrieval (needs an embedding provider, an index, and a data-retention policy)? | Embeddings work and any conversational search UI. | **Not yet — defer until D-006a's baseline is measured.** | Committing to a provider, index, and retention policy before there's a baseline to compare against risks paying for capability the typo-tolerant search already covers. |
| D-007 | Who can a collector share their cellar with, at what access level, for how long, and how is access revoked and audited? | The sharing/delegated-access feature entirely. | **Defer — ship nothing here for the first release.** If reopened later, default to a single "view-only, time-boxed" role rather than open-ended edit access. | The PRD already marks sharing as an optional slice that doesn't block core completion (audit finding F-05); the abuse cases and RLS surface are real enough to deserve their own dedicated approval later rather than a rushed default now. |
| D-008 | Which external storage/custody provider (if any) gets a real API/export integration, and on what lawful basis (no credential scraping, no bypassing provider controls)? | The provider-adapter feature entirely. | **Defer — no provider named yet; treat as a later, optional phase.** | Same as D-007: the PRD already treats this as non-blocking for core completion, and no provider's API/auth/export terms have been reviewed yet. |
| D-009 | When a bottle's drink window is closing, how does the user find out — an in-app list, or a push/email notification? | The drink-recommendation UI and any notification work. | **In-app shortlist only, ranked by soonest drink-window end; no push or email.** | The PRD's scope explicitly excludes notifications until a channel/infrastructure decision is made, so in-app is the only option actually available to default to. |
| D-010 | How are bottle-label and invoice photos stored and protected — bucket privacy, how long a signed URL stays valid, how long the photo is kept, and what gets scrubbed from logs/Sentry? | Any feature that persists a captured photo as evidence. | **Private per-tenant storage path; signed URLs live 3,600 s (matching what invoice URLs actually use today — approving this row makes that a deliberate policy for label evidence too, not an accident); evidence photo retained while its owning inventory row exists and deleted with it; evidence photos included in a collector's data export alongside their inventory; raw images/queries never sent to logs or Sentry replay.** | The PRD states the privacy/observability *goals* as non-functional requirements, but the concrete policy — retention, deletion, signed-URL TTL, export, log/Sentry redaction — is exactly what D-010 leaves OPEN (the package's own audit flagged that these lacked a decision gate). This row proposes one complete policy so a single approval closes the decision; amend any clause before approving if you want different numbers. |
| D-011 | When the vision model returns several candidate matches for a photographed label, how confident does the top match need to be before the user can accept it with one tap instead of confirming manually? | One-tap confirmation and any claim of "calibrated confidence" in the UI. | **Keep manual confirm-or-correct as the only path until a representative fixture set produces a measured, calibrated threshold.** The current `0.75` cutoff in the code is a heuristic, not a validated threshold, and should not be presented to the user as one. | The audit already flagged the `0.75` value as untested (finding F-09); shipping one-tap acceptance on an unvalidated number would let a wrong match get "confirmed" too easily. |

## What happens after approval

Once the owner records an answer for a row (here or via whatever channel the
owner prefers), that answer becomes the source-contract input for the
matching workstream in the implementation spec — it still has to go through
the normal `app_spec.txt` amendment / feature-ledger process before any
production code lands. This brief does not amend either document.
